# 典型场景时序图

> 六个最常见的使用场景，每个场景一张时序图 + 三句话说明。
> 离线场景由 `tests/test_offline.py` 覆盖，图中的类名可直接在代码中定位；
> 需要真实 MCP 与 LLM 的出行场景见 `demo/react-orchestration-2-agent/`（内存 A2A）与
> `demo/react-orchestration-2-agent-fastapi/`（YAML 配置、FastAPI HTTP A2A）。

---

## 场景 1：单轮多智能体编排（主管分派 → 工人并行 → 汇总）

对应 demo 示例 1。业务：客户申请退款，需要"政策核查"和"风险核查"
两个独立检查同时进行，都完成后汇总。

```mermaid
sequenceDiagram
    autonumber
    participant 调用方 as 调用方
    participant 图 as 工作流
    participant 主管 as RefundLeader（主管）
    participant 调度 as DispatchExecutor（调度器）
    participant 端点 as A2AWorkerEndpoint
    participant 运行器 as ProviderHarness
    participant 聚合 as AggregateExecutor

    调用方->>图: run(OrchestrationRequest：退款申请)
    图->>主管: create_plan(请求, 能力目录)
    主管-->>图: 计划（任务单：政策核查 + 风险核查）
    图->>调度: 派发计划
    par 工人A：政策核查
        调度->>端点: execute(任务单, 会话ID)
        端点->>端点: 打包载荷 → 传输 → 服务端 → 运行器执行
        端点-->>调度: 回执（completed）
    and 工人B：风险核查
        调度->>端点: execute(任务单, 会话ID)
        端点-->>调度: 回执（completed）
    end
    调度->>聚合: (请求, 计划, 回执列表)
    聚合-->>调用方: OrchestrationResult（completed + 汇总文本）
```

三句话：主管只出计划不执行；两个工人经 A2A 协议并行执行；
聚合器按"全部成功才算完成"判定终态。

## 场景 2：反思循环——内置确定性引擎（第一轮发现问题 → 第二轮补充检查）

对应 demo 示例 2。业务：政策核查发现"金额超阈值需高级风控复核"，
系统自动追加一轮风险检查，而不是把整个流程失败掉。

```mermaid
sequenceDiagram
    autonumber
    participant 图 as 工作流（含回边）
    participant 主管 as PolicyFirstLeader（第一轮主管）
    participant 调度 as DispatchExecutor
    participant 政策 as 政策 Worker（经 A2A）
    participant 反思 as ReflectExecutor + 反思规则
    participant 风险 as 风险 Worker（经 A2A）
    participant 聚合 as AggregateExecutor

    图->>主管: 第一轮计划
    主管-->>图: 只派"政策核查"
    图->>调度: 执行
    调度->>政策: 政策核查
    政策-->>调度: "满足七天条件；金额超 150 需高级风控复核"
    调度->>反思: 第一轮记录
    反思->>反思: 规则判断：政策要求升级 且 尚未升级
    反思-->>图: ReplanSignal（追加风险任务 + 新事实 escalated=risk-review）
    Note over 图: 回边：消息回到计划节点，开启第 2 轮
    图->>调度: 执行增量任务（风险复核，输入里带升级标记）
    调度->>风险: 高级风控复核
    风险-->>调度: "复核通过，无拒付风险"
    调度->>反思: 第二轮记录
    反思-->>图: FinalSignal（done：复核通过，结论齐备）
    图->>聚合: 全部两轮记录
    聚合-->>聚合: 终态 completed，rounds=2
```

三句话：第二轮的任务在第一轮执行前**不存在**，由反思规则基于第一轮
输出动态产生；新增的洞察（escalated=risk-review）合并进第二轮请求；
轮数上限（max_rounds）由确定性代码强制，防止无限循环。

## 场景 3：反思循环——Magentic 引擎（MAF 自带的多智能体循环）

对应 demo 示例 3。管理者（manager）每轮产出一个"进度账本"：
完成了吗？打转了吗？下一个谁发言？给他什么指令？

```mermaid
sequenceDiagram
    autonumber
    participant 调用方 as 调用方
    participant 管理者 as Magentic 管理者<br/>（DeterministicMagenticManager）
    participant 循环 as Magentic 内循环
    participant 工人A as 政策 Worker<br/>（MagenticWorkerAdapter → A2A）
    participant 工人B as 风险 Worker<br/>（MagenticWorkerAdapter → A2A）

    调用方->>循环: run(目标文本)
    管理者->>循环: 计划（plan）
    loop 每轮：进度账本（progress ledger）
        管理者->>管理者: 判断：完成了吗/打转吗/有进展吗/下一个谁
        alt 还有未发言的工人
            循环->>工人A: 指令（"请依据你的能力处理当前任务"）
            Note over 工人A: 每次"发言"= 一次真实 A2A 调用<br/>WorkerTask → 服务端 → 运行器 → 框架智能体
            工人A-->>循环: 执行结果文本（作为对话发言）
        else 全部发言完毕
            管理者-->>循环: 判定完成 → 汇总各工人发言
        end
    end
    循环-->>调用方: 终局发言 + 各 Worker 回执（经 collect 组装为 OrchestrationResult）
```

三句话：Magentic 的"参与者"就是被包装的 WorkerEndpoint，每次发言是
一次真实 A2A 调用；管理者是可替换的（demo 用确定性规则版，生产换
LLM 版）；连续打转会被 max_stall_count 护栏捕获并触发重新规划。

## 场景 4：人工审批与恢复（HITL，needs_approval → resume）

对应 demo 示例 5。业务：提交退款需要人工审批；审批通过后从中断处
继续执行，结构化结果全程保留。

```mermaid
sequenceDiagram
    autonumber
    participant 编排 as 编排器
    participant 端点 as A2AWorkerEndpoint
    participant 服务 as A2AWorkerService
    participant 门控 as 门控智能体<br/>（模拟 LangGraph interrupt / OpenAI 工具审批）
    participant 人工 as 人工审批

    编排->>端点: execute(任务单 g-1，resume=None，幂等键 wf:gate:1)
    端点->>服务: 载荷（无 resume 字段）
    服务->>门控: run(AgentRequest)
    门控-->>服务: AgentResult(needs_approval + 审批请求载荷)
    服务-->>端点: 回执（status=needs_approval, output 含结构化键）
    端点-->>编排: WorkerResult
    编排->>人工: 呈现审批请求
    人工-->>编排: 批准
    编排->>端点: execute(同一任务单 + resume={"approved": true}，<b>幂等键复用</b>)
    端点->>服务: 载荷（含 resume）
    服务->>门控: run(AgentRequest(resume=...))
    门控-->>服务: AgentResult(completed + data={"decision":"approved","refund_id":"RF-..."})
    服务-->>编排: 回执（completed，结构化键出现在 output）
```

三句话：暂停用 `status=needs_approval` 表达；恢复用 `resume` 载荷表达；
恢复时**幂等键必须复用**（同一件事），结构化键（decision/refund_id）
全程穿透协议层不丢失。

## 场景 5：工具与技能的声明式配置（同一声明，三种框架翻译）

对应 demo 示例 4。同一份 `HarnessSpec`（含一个 MCP 服务器 + 两个技能）
分别交给三种框架适配器构建，并演示跨框架的会话延续。

```mermaid
sequenceDiagram
    autonumber
    participant 声明 as HarnessSpec<br/>tools=[MCP服务器] skills=[内联技能, MCP技能]
    participant 校验 as ProviderHarness.validate()
    participant MAF as maf 框架适配器
    participant 会话 as 共享会话存储
    participant 回退 as fallback 框架适配器<br/>（无原生技能机制）

    声明->>校验: 五条检查（能力差集 / TOOL_LOOP / server_ref / 白名单 / 脚本）
    校验-->>声明: 通过（问题清单为空）
    声明->>MAF: build(spec)
    MAF-->>声明: MCPStreamableHTTPTool(...) + SkillsProvider(InlineSkill / MCPSkillsSource)
    声明->>MAF: run(请求1，会话 customer-001)
    MAF->>会话: 写入技能使用痕迹（facts["skill:refund-policy"]="used-by:maf-runtime"）
    声明->>回退: build(spec)  ← 同一份声明，不同框架
    回退-->>声明: OpenAI/ADK 构造语句；技能降级为 ContextItem 注入
    声明->>回退: run(请求2，同一会话)
    回退->>会话: 读到 maf 留下的痕迹 → 输出"[上下文延续]"
    回退->>会话: 写入自己的痕迹（键格式完全相同）
```

三句话：声明只有一份，翻译各干各的（有原生技能机制的翻译为原生，
没有的降级为上下文注入）；痕迹用统一的中立键格式写入会话，所以
任何框架留下的记录其他框架都读得懂——**换框架对话与能力记录都不断**。

## 场景 6：一次 A2A 调用的字段级数据流（协议翻译对照）

覆盖从任务单到回执的每个字段改名点（这是排查协议问题时最快的图）。

```mermaid
flowchart LR
    subgraph 编排侧
        WT["WorkerTask<br/>task_id / worker_id / instruction<br/>input / idempotency_key / depends_on / resume"]
    end
    subgraph 载荷["网络上传输的 JSON 字典"]
        P1["task_id / session_id / instruction<br/>input / idempotency_key / resume?"]
    end
    subgraph 服务侧
        AR["AgentRequest<br/>request_id ← task_id<br/>session_id<br/>input ← instruction<br/>metadata.idempotency_key<br/>resume"]
        ARS["AgentResult<br/>status / output / run_id / data"]
    end
    subgraph 回执
        P2["task_id / worker_id / status<br/>output{text + 结构化键} / error / remote_run_id"]
        WR["WorkerResult<br/>task_id / worker_id / status<br/>output / error / remote_run_id"]
    end
    WT -->|"Endpoint 组包"| P1
    P1 -->|"Service 解包"| AR
    AR -->|"Harness 执行"| ARS
    ARS -->|"Service 组包（data 并入 output）"| P2
    P2 -->|"Endpoint 归一化"| WR
```

三个改名点：`instruction → input`（进 agent）、`run_id → remote_run_id`
（出 agent）、`idempotency_key → metadata`（进扩展槽）。
`resume` 单向流（请求方向），`data` 反向流（结果方向）。
